# 精确重复资料分组与 JSON 导入设计

日期：2026-08-09

## 背景

当前资料模型把科研训练、实习实践、社会工作混在“学习和工作经历”，把论文、专利混在“学术成果”，并把竞赛与荣誉混在“奖励情况”。这种通用字段无法表达报名系统中的真实语义，尤其会把“获奖项目名称”和“竞赛名称”合并，导致导入、AI 匹配和自动填写错误。

## 目标

1. 将 3 个通用重复资料组替换为 7 个语义明确的重复资料组。
2. 让 JSON 导入、资料展示、字段匹配、重复行规划和对话框新增使用同一套精确字段定义。
3. 不迁移旧的三组数据；升级时仅删除这三组，用户通过新的 JSON 重新导入正确资料。
4. 保留基本信息、家庭成员、学习信息、外语水平和其他自定义资料。
5. 不把“无”创建为论文或专利记录。

## 新资料分组

| 显示名称 | 稳定 ID | 类型 | 字段顺序 |
| --- | --- | --- | --- |
| 科研训练 | `research_training` | repeat | 起止时间、项目名称、项目级别、排名 |
| 实习实践 | `internship_practice` | repeat | 起止时间、实习实践单位、主要工作内容 |
| 社会工作 | `social_work` | repeat | 起止时间、社会工作名称、主要工作内容 |
| 已发表论文 | `published_papers` | repeat | 作者、论文标题、刊物/会议名称、发表时间 |
| 已取得专利 | `granted_patents` | repeat | 专利权人、专利名称、授权或受理时间 |
| 学科竞赛 | `subject_competitions` | repeat | 获奖人、获奖项目名称、竞赛名称、获奖等级、获奖时间 |
| 本科期间校级以上（含）荣誉奖励 | `honors_awards` | repeat | 获奖名称、获奖等级、获奖时间 |

内部 ID 用于数据、匹配和迁移，显示名称只用于界面和页面语义提示。字段顺序是默认顺序；实际网页字段仍允许按标签、列名、邻近关系和 AI 结果重新排列。

每组还允许保存可选补充字段，以覆盖其他学校的表格要求；这些字段不要求用户每条都填写：

- 科研训练：项目描述、本人角色；
- 实习实践：实践类型、本人角色；
- 社会工作：本人角色、组织/单位；
- 已发表论文：论文类型、发表状态、分区、本人排名；
- 已取得专利：专利类型、专利状态、专利号、本人排名；
- 学科竞赛：主办单位、描述、本人排名；
- 荣誉奖励：主办单位、描述、本人排名。

必需字段仍保持用户指定的精确语义；可选字段只用于目标页面存在相应列时的增强填充。

## 版本升级与清理

版本从 `1.4.0` 升到 `1.5.0`。升级脚本只删除 section ID 为 `experience`、`academic`、`awards` 的旧重复资料组，然后创建上述 7 个新组（若已存在则保持已有新组内容）。

升级脚本不得删除以下内容：

- `basic`、`family`、`education`、`language`；
- 用户创建的自定义 block；
- API 设置、页面缓存、任务记录、材料文件。

清理操作必须幂等：重复执行不会重复删除或重复创建。升级前不自动把旧内容猜测性迁移到新组，也不在日志中输出个人资料值。

## JSON 导入约定

导入文件使用现有 profile bundle 结构，并为每个新分组提供 `sectionId`、`title`、`templateFields` 和 `items`。每个 item 的字段键必须属于该分组的 `templateFields`。

字段校验规则：

- 精确字段名优先；同义词只在明确的字段别名表中转换。
- 未知字段进入导入结果中的“未识别字段”列表，不自动并入其他字段。
- “已发表论文”和“已取得专利”在源数据为“无”时使用空 `items` 数组。
- “导入/更新 JSON”按现有同名 block 更新；“新增 JSON”只追加不重复记录。
- 不提交 API Key、身份证号、联系方式或个人资料 JSON 到 Git。

学科竞赛示例：

```json
{
  "获奖人": "测试同学等（队长）",
  "获奖项目名称": "OopsOS：基于xv6-RISCV的小型操作系统内核扩展",
  "竞赛名称": "全国大学生计算机系统能力大赛操作系统设计赛",
  "获奖等级": "华东区域赛三等奖",
  "获奖时间": "2026年1月"
}
```

## 匹配与自动填写

重复资料规划器、字段本地匹配器和 AI 字段匹配器都读取新的 section definition。匹配优先级为：

1. 同分组的精确字段名；
2. 同分组的受控别名；
3. 结构化字段组合（例如同一竞赛行的项目名称、竞赛名称、等级、时间）；
4. AI 建议，仅作为低置信度候选，并保留人工确认状态。

对于一个大文本框，仍支持把同一条记录的多个字段按明确模板聚合；对于拆开的多个子字段，按字段键独立填写。无证据时不把项目名称、竞赛名称、奖励名称互相替代。

### 目标表结构适配

资料库不因某个学校的页面结构而改变。扫描页面后，系统先建立目标字段 schema，再将 7 个资料分组投影到目标 schema：

- `论文情况` ← `published_papers`；
- `项目经历` ← `research_training`、`internship_practice`、`social_work`；
- `获奖情况` ← `subject_competitions`、`honors_awards`；
- 其他页面分组由字段标签、表格列名和上下文决定来源。

投影分两层：

1. 本地确定性映射处理精确字段、受控别名、时间/等级/排名等结构化值；
2. 只有多个来源都可能匹配、字段是长文本、或页面把多个源字段合并时，才调用 API 生成候选映射。

每个候选保留来源字段、目标字段、置信度和解释。低于阈值的候选只显示为“需要确认”，不会直接覆盖网页内容。

### 长问题与大文本框

面对“个人项目介绍”“科研经历说明”“申请理由”等长问题：

- 先根据题目、字段标签和页面上下文分类问题类型；
- 只检索相关资料组和相关记录，不发送整份资料库；
- 先生成结构化事实摘要，再按题目生成草稿，事实和表达分两步可追溯；
- 对超过单次请求长度的内容按语义段落分块，最后进行一次受限合并；
- 合并时保留原始事实、数字、日期和排名，禁止模型自行补全；
- 草稿填入后默认标为“需审核”，用户修改后不会被下一步扫描或 API 回写覆盖；
- API 失败、超时或返回不完整时保留本地匹配结果，并允许手动重试。

API 请求携带目标 schema、题目文本、相关候选记录、模型模式和长度预算，而不是固定 prompt。Fast 模式使用更小的候选集和单轮请求；标准模式允许两阶段摘要/草稿流程。两种模式都遵守相同的事实约束和高风险操作拦截。

API 结果缓存键包含网站/项目标识、页面语义键、字段指纹、资料版本、模型和模式。相同页面在资料未变化时直接复用缓存，资料或题目变化后自动失效。

重复行和重复对话框新增继续沿用现有的安全规则：只操作当前目标记录，保存成功必须有关闭、新记录行或此前不存在的值等可验证证据；不点击最终提交、确认报名、志愿、导师、承诺、验证码或支付控件。

## 验证范围

- 新 section definitions、字段别名和 bundle 解析单元测试；
- 7 个源分组到“论文情况 / 项目经历 / 获奖情况”的目标 schema 投影测试；
- 长文本分块、摘要、草稿和缓存失效测试；
- 旧三组清理与新七组创建的幂等升级测试；
- 竞赛 6 条记录逐字段断言，确保项目名和竞赛名不合并；
- 科研训练、实习实践、社会工作、荣誉奖励逐字段断言；
- 空论文/专利不生成虚假记录；
- 现有基本资料、家庭成员、学习信息、语言成绩和既有重复行测试回归；
- TypeScript 编译、生产构建和现有自动化测试。

## 非目标

- 本次不开发 Word/PDF 智能资料解析。
- 本次不实现报名提交或任何高风险操作。
- 本次不把旧三组数据自动分类迁移。
