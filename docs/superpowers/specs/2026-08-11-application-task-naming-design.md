# 保填 Agent 2.1.1：报名任务稳定编号与自定义名称设计

## 1. 目标

当前任务名称由页面身份识别结果直接生成。它存在两个问题：页面已经回显申请人的本科资料时，来源院系可能被误认为目标院系；同一学校同时报名多个项目、但页面没有可靠院系信息时，各任务难以区分。页面再次扫描还会覆盖 `displayName`，因此不能直接把用户编辑后的文本写回这个字段。

本次改动建立三层、可降级且稳定的任务命名机制：

1. 可靠识别目标学校和目标院系时，显示 `学校 · 院系`。
2. 识别到学校、但没有可靠目标院系时，按学校分配并持久化 `学校 · 项目 N`。
3. 用户自定义名称时，自定义名称永久优先，直到用户主动恢复自动名称。

本次同时禁止使用申请人的本科院校、本科院系和本科专业生成目标报名任务名称。Agent 可以处理有歧义的页面身份，但只能依据页面证据判断；证据不足时必须返回空院系并使用项目编号，不能猜测。

## 2. 范围

本次包含：

- 分离自动身份、稳定项目编号、自定义名称和最终显示名称。
- 同一学校的无院系项目分别编号为项目 1、项目 2、项目 3；另一所学校重新从项目 1 开始。
- 在插件首页当前任务和统一审核中心支持编辑名称、取消编辑和恢复自动名称。
- 后续页面扫描和 Agent 身份更新不得覆盖用户自定义名称。
- 排除申请人的本科院校、本科院系和本科专业，修复来源院系被当作目标院系的问题。
- 为同一标签页切换到同站不同报名项目补充身份校验，避免项目记录串入原任务。
- 将扩展版本升级为 `2.1.1`，更新构建和发布说明。

本次不包含：

- 让用户编辑学校、院系和项目三个独立结构化字段；用户编辑的是最终显示名称。
- 依赖 API 才能完成编号、恢复名称或任务隔离。
- 自动提交、保存报名、确认报名或其他高风险操作。

## 3. 名称优先级

任务最终显示名称由一个纯函数统一生成，插件首页、连续填写记录和统一审核不得各自拼接名称。

优先级为：

```text
非空 customDisplayName
→ institutionName · departmentName
→ institutionName · 项目 projectOrdinal
→ siteTitle · 项目 projectOrdinal
```

规则：

- `departmentName` 只有在页面证据可靠且不是申请人来源院系时才可使用。
- 页面识别到 `projectName` 时将其保存在自动身份中，可在详情或辅助文本显示，但只要缺少可靠院系，任务主名称仍按用户确认的规则使用 `项目 N`。
- `projectOrdinal` 是持久化编号，任务刷新、跳页、浏览器重启、暂停或恢复后不得变化。
- 用户清空自定义名称等同于“恢复自动名称”。
- 用户自定义名称去除首尾空白；空字符串不保存；最大长度为 60 个 Unicode 字符。
- 所有名称均作为文本转义后渲染，不能作为 HTML 注入界面。

示例：

```text
中山大学 · 计算机学院
中山大学 · 项目 1
中山大学 · 项目 2
复旦大学 · 项目 1
```

用户将第二项改为 `中大 · 计院人工智能夏令营` 后，后续扫描只更新后台自动身份，最终仍显示用户名称。恢复自动名称后，若此时已经可靠识别院系则显示学校和院系，否则恢复为原来的稳定项目编号。

## 4. 数据模型

`ApplicationTask` 增加以下可选字段，以兼容已有本地任务：

```ts
interface ApplicationTask {
  // 现有字段略
  automaticIdentity?: AgentApplicationIdentity;
  projectOrdinal?: number;
  projectOrdinalScope?: string;
  customDisplayName?: string;
}
```

现有 `displayName` 暂时保留为兼容和快照字段，但只能由统一名称解析函数写入，不再作为用户输入和自动身份的唯一存储位置。

旧任务迁移采用惰性兼容：

- 缺少 `automaticIdentity` 时，首次页面分析后补齐。
- 缺少 `projectOrdinal` 且没有可靠院系时，首次需要显示编号时分配。
- 旧 `displayName` 不自动当作用户自定义名称，避免把历史错误识别结果永久锁定。
- 新字段缺失时仍能读取旧任务，不阻塞插件启动。

## 5. 稳定编号分配

编号以规范化后的目标学校名为首选作用域；目标学校尚未识别时，以 `siteOrigin` 为临时作用域，并把实际作用域保存在 `projectOrdinalScope`。识别到学校后，将临时作用域迁移到学校作用域。

编号分配由 background 中的单一串行入口执行，不能在 popup 渲染时临时计算：

1. 读取未归档和已归档任务中同一学校作用域的已占用编号。
2. 当前任务已有正整数编号且 `projectOrdinalScope` 与当前作用域一致时直接保留。
3. 否则在当前作用域分配最小未占用正整数。
4. 从临时域迁移到学校域时，优先保留原编号；若该编号已被更早创建的任务占用，则只为当前迁移任务重新分配最小未占用编号。
5. 将编号、作用域与任务一起持久化后再返回界面。

归档任务继续占用原编号，防止重新打开或恢复任务后名称变化。新任务不复用已归档任务编号。同一来源网站的多个项目通常会在首次分配时就共享同一个临时作用域，因此学校识别完成后不会改号；只有两个不同来源域后来被确认属于同一学校且发生编号冲突时，才允许在身份迁移时进行一次确定性重排。迁入学校作用域后编号保持稳定。编号只承担展示区分作用，不参与页面记录、Agent 缓存或材料缓存的身份键。

为避免两个标签页同时创建任务时得到相同编号，编号分配和任务保存需要进入同一个 background 串行队列，或使用一次读取、分配、写回的原子更新辅助函数。

## 6. 页面身份与 Agent

页面身份输入必须区分“页面证据”和“申请人来源资料”，不能再把所有字段值混成同一个候选列表。

申请人来源身份至少包含：

```json
{
  "institutionName": "合肥工业大学",
  "departmentName": "计算机与信息学院",
  "majorName": "计算机科学与技术"
}
```

页面证据分为：

- 页面标题、可见主标题、Logo 文本和面包屑；
- 当前报名项目、招生单位、申请院系等明确标签及已选值；
- URL 中稳定的项目参数；
- 页面说明和步骤标题；
- 普通申请人资料字段值，单独放入 `applicantValues`，不得作为目标身份的首选证据。

本地识别先执行明确排除：与来源学校、来源院系或来源专业相同的普通表单值不进入目标学校/院系候选。若本地证据唯一，直接使用；若存在多个合理候选且 API 已配置，则调用受约束的身份 Agent。

身份 Agent 只返回：

```json
{
  "institutionName": "中山大学",
  "departmentName": "计算机学院",
  "projectName": "2027年优秀大学生夏令营",
  "evidenceTexts": ["页面中真实存在的证据文本"],
  "confidence": "high"
}
```

本地必须验证学校、院系和证据文本确实来自允许的页面证据集合。Agent 返回空院系是合法结果；返回本科来源院系、页面中不存在的院系或没有证据的院系时拒绝该值并回退到 `项目 N`。API 失败、超时或 5xx 不影响编号和用户自定义名称。

身份 Agent 结果按页面结构、项目 URL、来源身份、模型配置和协议版本缓存，避免同一任务重复调用。

## 7. 用户界面

### 7.1 当前网站

插件首页“当前网站”名称右侧增加轻量编辑按钮。点击后在原位置显示单行输入框，并提供：

- 保存；
- 取消；
- 已存在自定义名称时显示“恢复自动名称”。

保存成功后当前任务卡片立即刷新。编辑过程不启动页面扫描、不调用 API、不改变自动填写状态。

### 7.2 统一审核

统一审核的每个任务卡片使用同一个名称解析函数，并提供相同的编辑和恢复入口。修改后首页、任务列表、最终检查标题和统一审核同步显示新名称。

### 7.3 错误处理

- 空名称提示“请输入名称”，不保存。
- 超过 60 个字符时在输入端限制并在 background 再次校验。
- 任务已经归档仍允许改名；任务不存在时提示刷新任务列表。
- 保存失败时保留输入内容并显示错误，不回退成看似成功的旧名称。

## 8. 任务隔离

标签页绑定不能只检查 `tabId`。每次继续使用已绑定任务前，应比较当前页面与任务的项目身份：

- `siteOrigin`；
- 规范化 URL 中的项目参数或哈希参数；
- 已识别的学校和项目信息；
- 已保存页面集合中的 URL/页面签名。

如果同一标签页切换到同站另一个明确项目，创建或切换到独立任务，并单独分配该学校的项目编号。身份存在歧义时不自动合并两个任务，保留当前任务并提示用户确认。显示编号只用于识别，不能代替真实任务 ID 或页面项目键。

## 9. 消息与数据流

新增 background 消息：

```ts
{ type: 'renameApplicationTask'; taskId: string; customDisplayName: string }
{ type: 'restoreAutomaticTaskName'; taskId: string }
```

处理流程：

```text
popup / 统一审核
→ background 校验任务和名称
→ 更新 customDisplayName
→ 通过统一解析函数重算 displayName
→ 持久化任务
→ 返回更新后的任务
→ 所有任务视图刷新
```

页面分析流程只更新 `automaticIdentity`、必要时分配 `projectOrdinal`，然后通过统一解析函数刷新兼容用 `displayName`；不得清空或重写 `customDisplayName`。

## 10. 测试与验收

测试必须先失败再实现，覆盖：

- 同一学校三个无院系任务稳定得到项目 1、项目 2、项目 3。
- 另一所学校重新从项目 1 开始。
- 归档、刷新、跳页和重新载入后编号不变，新任务不复用归档编号。
- 识别出可靠院系后自动名称从项目编号升级为学校和院系，内部编号继续保留。
- 后续院系证据消失时仍回退到原编号，不重新编号。
- 用户自定义名称优先于自动身份，页面扫描和 Agent 更新不能覆盖。
- 恢复自动名称后正确显示学校和院系，或原项目编号。
- 本科院校、本科院系和本科专业不能作为目标任务身份。
- API 返回无页面证据的院系时拒绝并使用项目编号。
- API 失败时编号、自定义名称和任务读取保持可用。
- 同一标签页切换同站不同项目不会合并页面历史、材料或最终审核状态。
- 当前网站与统一审核的编辑、取消和恢复行为一致。
- 名称长度、空白和 HTML 特殊字符校验有效。

真实浏览器验收只检查任务命名和任务隔离，不点击最终提交：

1. 同一学校打开三个不同项目，确认显示项目 1、项目 2、项目 3。
2. 刷新和切换页面，确认编号稳定。
3. 自定义第二个任务名称，确认首页和统一审核同步，后续扫描不覆盖。
4. 恢复自动名称，确认回到原编号或可靠院系名。
5. 在同一标签页进入另一个项目，确认不会串入原任务历史。
